# Can Type RTO 축열재(세라믹) 막힘 사전예측 시스템

대양 RTO **Can type**(Rotary 1-Can: 8~12개 섹터 베드를 단일 로터리 밸브가 흡입/배출/퍼지로
전환, 약 3RPM) **20대**의 축열재 막힘을 운전 데이터로 조기에 정량화합니다.

- **설비 건전도 100점** — 관련 파라미터 16종을 막힘 연관도에 따라 차등 가중해 합산
- **동급기 상호비교** — 동일 사양 병렬 호기끼리 비교해 단독 이상 호기를 즉시 지목
- **변화추이 분석** — 추세 기울기 · 변화점 검출 · 운전 한계 도달 시점 예측
- **점검 가이드** — 지표 조합으로 고장모드를 판정하고 구체적 조치를 제시

```bash
pip install -r requirements.txt
python data/sample/generate_fleet_sample.py   # 20대 가상 데이터 생성
streamlit run app/streamlit_app.py            # 대시보드
```

## 대상 설비 20대

| 계열 | 호기 | 대수 | 처리 대상 |
|---|---|---:|---|
| VRT-A31101 / A31102 | A, B | 2 + 2 | **유기배기** (고농도 VOC) |
| VRT-A31103 / A31105 | A~E | 5 + 5 | 유기배기 |
| ORT-A31101 / A31102 / A31103 | A, B | 2 + 2 + 2 | **냄새배기** (저농도·대풍량) |
| | | **20** | |

VRT(유기배기)와 ORT(냄새배기)는 **막힘 기전이 다릅니다.** 유기배기는 응축성 유기물·타르
고착이, 냄새배기는 분진 누적이 주 원인이라 오염 속도와 권장 세정 주기를 다르게 잡습니다
(`config/fleet.yaml` 의 `types` 블록). 같은 형식 안에서도 계열마다 풍량·사이즈가 달라
설비 사양을 개별 관리합니다.

## 왜 차압만 보면 안 되는가

현장에서 막힘 판단은 보통 차압 하나로 합니다. 그런데 차압은 막힘 말고도 **생산량과
가스 온도**에 따라 크게 변합니다. 풍량이 20% 늘면 차압은 23~44% 오르고, 겨울과 여름의
유입가스 온도 차이만으로도 10% 넘게 움직입니다. 이 변동을 걷어내지 않으면
**생산량이 늘어난 것을 막힘으로 오판**하고, 반대로 감산 중에 진행된 막힘은 놓칩니다.

그래서 모든 지표를 기준 조건으로 환산한 뒤에 비교합니다.

```
ΔP_norm = ΔP × (Q_ref/Q)^n × (T_ref/T)
```

`n`(유량 지수)은 축열재 형상에 따라 다릅니다 — 허니컴은 층류 지배로 ≈1.0~1.2, 랜덤 새들은
난류로 ≈1.8~2.0. 이 값을 상수로 박아두지 않고 **베이스라인 구간 실측에서 회귀로 피팅**해
설비 실제 특성에 맞춥니다. (샘플 데이터 검증: 생성에 쓴 1.150을 1.148, R²=0.999로 복원)

배출온도·팬 주파수·연료량처럼 운전조건 의존도가 큰 값은 절대 비교 대신
**조건부 기준모델의 잔차**를 씁니다. "같은 풍량·같은 VOC 농도에서 얼마나 벗어났는가"를
보는 편이 오탐이 훨씬 적습니다.

## 100점 배점

건전도 = `100 − Σ(지표별 열화도(0~1) × 배점)`. 100점 = 세정 직후 수준.

배점은 **막힘과의 인과 근접도** 순으로 차등했습니다 — 직접 증거 > 성능 결과 > 누적 스트레스.

### A군. 유동저항 — 45점 (막힘의 직접 증거)

| 지표 | 배점 | 내용 |
|---|---:|---|
| A1 정규화 베드 차압 | **16** | 풍량·온도 보정 차압의 베이스라인 대비 비율 |
| A2 차압 상승 기울기 | 9 | 30일 Theil-Sen robust 기울기 — "얼마나 빨리 나빠지는가" |
| A3 송풍기 부하 상승 | 7 | 동일 풍량 기준 인버터 주파수(없으면 전류) 비율 |
| A4 댐퍼 개도 여유 감소 | 5 | 목표 풍량 유지를 위한 개도 상승 = 여유 소진 |
| A6 동급기 대비 편차 | 5 | 동일 계열 병렬 호기의 정규화 차압 중앙값 대비 비율 |
| A5 차압 변동성 | 3 | 정규화 차압의 일중 변동계수 — 국부 폐쇄 징후 |

### B군. 열교환 성능 — 25점

| 지표 | 배점 | 내용 |
|---|---:|---|
| B1 열회수효율(TER) 저하 | **10** | `(T_comb − T_stack)/(T_comb − T_in)` 의 하락 폭 |
| B2 스택 배출온도 상승 | 6 | 동일 조건 기준모델 대비 상승분 |
| B3 섹터 간 출구온도 편차 | 5 | 섹터별 표준편차 — **채널링 판정의 핵심** |
| B4 연소실 온도 안정성 | 4 | 설정치 대비 편차의 이동표준편차 |

### C군. 에너지·처리 성능 — 20점

| 지표 | 배점 | 내용 |
|---|---:|---|
| C1 연료 원단위 상승 | **8** | 단위 처리풍량당 연료 사용량 비율 |
| C2 버너 가동률 상승 | 5 | 동일 VOC 부하 대비 on-time 비율 |
| C3 VOC-연료 괴리 | 4 | VOC가 높으면 연료는 줄어야 정상 — 회귀 잔차 |
| C4 배출농도 악화 | 3 | TMS 배출농도 비율 |

### D군. 누적 오염 부하 — 10점

| 지표 | 배점 | 내용 |
|---|---:|---|
| D1 누적 VOC 부하 | 5 | 마지막 세정 이후 `∫(VOC × 풍량)dt` / 설계 부하 |
| D2 누적 운전시간 | 5 | 마지막 세정 이후 운전시간 / 권장 세정 주기 |

> **연료(C1)는 증폭 지표입니다.** 열회수효율이 1%p 떨어지면 보조연료는 20~30% 늘어납니다.
> 민감도가 높아 조기 신호로 유용하지만, 임계치를 좁게 잡으면 초기 열화에서 곧바로
> 만점 감점되어 분해능을 잃습니다. `severe` 를 2.0배로 넓게 잡은 이유입니다.

### 동급기 상호비교(A6)가 따로 필요한 이유

A1(자기 베이스라인 대비)에는 치명적인 약점이 있습니다. **베이스라인 자체가 오염돼 있으면
무력합니다.** 이미 막힌 상태에서 데이터 수집을 시작하면 그 상태를 "정상"으로 학습해
막힘을 영영 못 잡습니다.

A6은 이 문제를 받지 않습니다. 옆 호기와의 비교는 내 기준값이 틀려도 성립하기 때문입니다.
20대를 병렬 운전하는 현장에서만 쓸 수 있는 안전장치입니다.

둘은 서로를 보완합니다.

| A1 (자기 기준) | A6 (동급기 기준) | 의미 | 조치 방향 |
|---|---|---|---|
| ↑ | ↑ | 이 호기만 나빠짐 | **해당 호기 우선 정비** |
| ↑ | ≈1 | 계열 전체가 함께 나빠짐 | **설비가 아니라 유입측 조사** |
| ≈1 | ↑ | 베이스라인 오염 의심 | 정상 구간을 직접 지정할 것 |
| ≈1 | ≈1 | 정상 | — |

동일 계열이 2대 미만이면 A6은 자동 제외되고 45점이 나머지 A군 지표로 재배분됩니다.
2호기 계열(A·B)은 비교 대상이 1대뿐이라 5호기 계열보다 근거가 약하며, 두 대가 함께
나빠지면 드러나지 않습니다 — 대시보드에 비교 대수를 함께 표기합니다.

|---|---|---|---|
| 🟢 A | 90–100 | 정상 | 일상 점검 유지 |
| 🟡 B | 75–89 | 초기 열화 | 추세 감시 강화 · 차압 주간 기록 |

## 점검 가이드 — 지표 조합으로 원인을 가른다

점수만으로는 무엇을 점검할지 정해지지 않습니다. 같은 68점이라도 원인이 균일 분진이면
bake-out 으로 끝나지만, 실리카 고착이면 bake-out 은 시간 낭비입니다.

| ΔP_norm | TER | 섹터 편차 | 추정 원인 | 조치 |
|---|---|---|---|---|
| ↑ | 유지 | 작음 | 균일 미세 파티클 누적 | **online bake-out** |
| ↑↑ | ↓ | 큼 | 국부 폐쇄·채널링 (타르/실리카) | 세정 또는 상부층 부분 교체 · Si 성분 분석 |
| ↑ 급상승 | ↓ | 중간 | VOC 스파이크 후 폴리머 응축 | 전처리 필터·미스트 제거기 점검 |
| **정상** | ↓ | 큼 | ⚠️ **막힘 아님** — 축열재 침하 / 로터리밸브 씰 누설 | 밸브 씰·충진 상태 점검 (**세정 무효**) |
| ↓ (감소) | ↓ | 큼 | 축열재 유실·바이패스 | 베드 내부 육안 점검 · 그레이팅 확인 |
| 정상 | 유지 | 정상 + 연료↑ | 버너·제어계 이상 | 연소 튜닝 · 열전대 교정 |

20대 병렬 운영에서만 판정 가능한 두 가지가 추가됩니다.

| A1 | A6 | 판정 | 조치 |
|---|---|---|---|
| ↑ | ↑↑ | **동급기 대비 단독 이상** | 해당 호기를 계열 내 정비 1순위로. 정상 호기와 유입 배관·댐퍼·전처리 비교 점검 |
| ↑ | ≈1 | **계열 전체 동반 열화** | 개별 정비 아님 — 공정측 배출조건 변화, 공통 전처리 설비(집진기·스크러버) 점검. 계열 bake-out 동시 계획 |

네 번째 행이 이 시스템을 만든 이유입니다. 차압은 정상인데 효율만 떨어졌다면 유로가
막힌 게 아니라 **가스가 축열층을 우회**하고 있다는 뜻입니다. 이걸 막힘으로 오진하면
효과 없는 세정에 정지 시간을 씁니다. 판정 규칙은 `config/weights.yaml` 의
`failure_modes` 에 있으므로, 새로운 고장 패턴은 코드 수정 없이 규칙만 추가하면 됩니다.

## 현장 적용 절차

### 1. 설비 사양 (`config/fleet.yaml`) — 가장 먼저 채울 것

계열 단위로 적으면 호기가 자동 전개됩니다. 설비 ID = `{계열}{호기}` → `VRT-A31101A`.

```yaml
series:
  - {id: VRT-A31103, units: [A, B, C, D, E], design_flow_cmm: 600, design_max_dp_mmh2o: 220}
```

상속 우선순위는 `overrides > series > types > defaults` 이므로, 아는 사양부터 채우면 됩니다.

> ⚠️ **현재 풍량·설계차압·VOC 농도는 자리표시자입니다.** 실제 사양으로 교체해야
> 운전 한계 도달 예측(RUL)과 정상운전 구간 판정이 맞습니다.
> 축열재 형상(`media_type`)은 유량 지수 초기값에만 쓰이고 데이터가 쌓이면 자동 교정되므로
> 부담이 적습니다.

### 2. 베이스라인 기준값 — 지금부터 누적한다면 반드시 확인

데이터를 지금부터 모으기 시작하면 **"세정 직후 깨끗한 구간"이 데이터에 없을 수 있습니다.**
그 상태로 자동 선정에 맡기면 이미 오염된 구간을 정상으로 학습해 막힘을 놓칩니다.
세 가지 경로를 우선순위대로 지원합니다.

```yaml
baselines:
  VRT-A31103C:
    period: {start: 2026-03-15, end: 2026-03-29}          # ① 깨끗했던 구간 직접 지정
  VRT-A31101A:
    manual: {dp_bed: 78, ter: 0.95, flow: 900, t_in: 40}  # ② 시운전/설계값 직접 입력
  # ③ 미지정 → 마지막 full_clean 이후 14일, 없으면 데이터 앞 14일
```

③으로 잡히면 대시보드와 리포트에 **"⚠️ 자동 추정"** 경고가 뜹니다. 그 상태에서는
동급기 대비(A6) 열이 더 믿을 만합니다.

②(수동 입력)를 쓰면 조건부 기준모델을 학습할 실측 구간이 없으므로 잔차 기반 지표
(A3·B2·C2·C3)가 채점에서 빠지고, 남은 지표가 100점을 나눠 갖습니다.

### 3. 태그 매핑 (`config/tags.yaml`)

20대를 한 파일로 받는 경우 `fleet` 블록의 규칙으로 설비별 컬럼을 찾습니다.

```yaml
fleet:
  tag_pattern: "{equipment}_{suffix}"    # → VRT-A31101A_DP_BED
  shared: {timestamp: TIMESTAMP}         # 설비명 없이 공유하는 컬럼
  suffixes:
    dp_bed: DP_BED
```

특정 설비의 특정 태그만 이름이 다르면 `equipment_overrides` 로 예외 처리합니다.
매핑이 틀리면 지표가 조용히 빠져 점수만 이상해지므로, 대시보드 **설정** 탭의
**태그 자동 감지** 표에서 20대 전부 `✅ 정상`인지 먼저 확인하십시오.

보유하지 않은 태그는 비워 둡니다 — 해당 지표는 자동 제외되고 **남은 지표끼리 100점을
재배분**합니다. 필수 태그는 `timestamp, dp_bed, flow, t_comb, t_in, t_stack` 6종입니다.

### 4. 정비 이력 · 임계치

정비 이력 태그는 보통 DCS 에 없으므로 `config/fleet.yaml` 의 `maintenance_events` 에
설비별로 적습니다. `full_clean` / `media_replace` 는 베이스라인을 리셋합니다.

임계치는 `onset`(정상 한계)과 `severe`(만점 감점) 사이에서 열화도가 0~1로 선형 사상됩니다.
대시보드 **설정** 탭에서 바꾸면 즉시 재채점되니, 현장 감각에 맞는 값을 찾은 뒤 파일에
반영하십시오.

### 5. 데이터 누적 (1시간 단위)

로더가 **여러 파일과 폴더**를 받습니다. 월별 export 를 폴더에 그대로 쌓으면 되고,
구간이 겹치면 나중 파일이 이깁니다(재추출본 우선).

```python
from rto_health.io_loader import read_frames
df = read_frames("data/monthly/")       # 폴더째 병합 + 중복 제거
```

## ⚠️ 가중치는 아직 검증된 값이 아닙니다

현재 배점은 RTO 물리·정비 문헌에 근거한 **공학적 추정치**이며, 통계적으로 검증된 값이
아닙니다. 실제 정비 이력이 쌓이면 재보정해야 합니다.

```bash
python -m rto_health.calibrate -i <운전데이터>          # 제안만 확인
python -m rto_health.calibrate -i <운전데이터> --apply  # weights.yaml 에 반영
```

각 지표의 열화도와 '다음 정비까지 남은 시간'의 Spearman 상관을 구해, 실제로 막힘을
예고한 지표에 배점을 더 줍니다. 그룹 총점(A 45 / B 25 / C 20 / D 10)은 유지하고
**그룹 안에서만** 재배분합니다 — 인과 근접도에 따른 그룹 구조는 물리적 근거이므로
데이터 한 사이클로 뒤집지 않습니다. 유의미한 보정에는 세정/교체 이력 **2회 이상**이
필요하며, 그 전에는 정규화 차압을 대리 지표로 쓰되 경고를 함께 표시합니다.

20대 운영은 이 재보정에 유리합니다 — 정비 이벤트가 20배 빨리 모입니다.

### 태그를 추가하면 좋아지는 것

로터리 밸브 RPM·절환주기와 bake-out 실시 이력이 태그로 확보되면 밸브 씰 누설 진단이
현재의 온도편차 기반 간접 추정에서 직접 측정으로 바뀝니다. Can type 에서 밸브 씰은
최빈 고장부이므로 정확도 향상 폭이 큽니다.

### 파이프라인

단일 설비:

```
로딩 → 정제 → 정상구간 판정 → 베이스라인 선정 → 물리 보정 → 일 집계
     → 지표 산출 → 채점 → 추세/변화점/RUL → 고장모드 판정
```

20대 통합은 동급기 비교 때문에 2패스로 나뉩니다 — 전 설비의 일 집계가 나와야
계열 중앙값을 구할 수 있기 때문입니다.

```
패스 1  설비별 전처리 → 일 집계          (pipeline.prepare)
패스 2  계열별 동급기 중앙값 산출
패스 3  설비별 지표(A6 포함) → 채점 → 판정 (pipeline.score_prepared)
```

**한 대가 실패해도 나머지는 그대로 나옵니다** — 계측 고장 설비 하나 때문에 전체가
멈추면 안 되므로, 실패 설비는 `FleetAnalysis.failed` 에 사유와 함께 기록됩니다.

기동/정지/저부하 구간은 지표 계산에서 제외합니다(`steady_state` 설정). 과도구간의
차압과 온도를 섞으면 막힘과 무관한 변동이 지표를 흔듭니다.

### 주요 검증 항목

- 풍량이 4배 변해도 정규화 차압은 불변 — 그러면서 실제 1.8배 막힘은 그대로 검출
- 유량 지수 회귀가 데이터 생성값(1.150)을 1.148 / R²=0.999 로 복원
- CUSUM 이 주입한 막힘 개시일(7/30)을 8/9에 검출, 정상 운전에서는 오알람 0건
- bake-out 실시일(5/19, 9/22)을 '개선' 방향 변화점으로 검출
- 차압 정상 + 효율 저하 + 섹터 편차 큼 → 막힘이 아닌 **씰 누설**로 정확히 판정
- 태그를 빼도 배점 합계 100 유지 및 잔여 지표 재배분
- fleet.yaml 이 정확히 20대로 전개되고 상속 우선순위가 값별로 지켜짐
- 오염된 구간을 베이스라인으로 잡으면 점수가 과대평가됨을 실측으로 확인(경고가 필요한 이유)
- 계측 고장 설비 1대를 넣어도 나머지 19대가 정상 산출됨
- 월별 파일을 겹치게 쌓아도 중복 없이 병합됨

CUSUM 은 값의 수준이 아니라 **일간 증분**을 감시합니다. 축열재는 정상 상태에서도 아주
느리게 오염되므로 수준 기반 CUSUM 은 그 정상 드리프트마저 누적해 결국 반드시 알람을
냅니다. 우리가 찾는 것은 "값이 높아졌다"가 아니라 "나빠지는 속도가 달라졌다"입니다.
